# نظام إدارة مسؤوليات المشتريات — مراجعة معمارية

> **الحالة:** تصميم مقترح للمراجعة — **لم يُنفَّذ أي تعديل بناءً عليه.**
> **الهدف:** نقل مصدر المسؤولية من بنود طلبات الموردين (`rfq_items`) إلى بنود طلبات
> العملاء (`customer_rfq_items`)، وجعل كلمات التصنيف قابلة للإدارة من الواجهة.
> **القيد:** لا commit / push / PR / deploy.

---

## 1. الملخص التنفيذي

الوضع الحالي يبني المسؤولية على الجدول **الخطأ** بالنسبة لدورة العمل في قرطبة:

- الجدول `rfq_item_assignments` يشير إلى `rfq_item_id` (طلب تسعير **مورد**).
- طلب العميل (`customer_rfq_items`) يحمل `category_id` بالفعل في الـDDL لكن **لا
  يُملأ ولا يُقرأ** من أي مسار.

النتيجة: المسؤولية تُنشأ **بعد** إصدار طلب المورد، بينما هي فعليًا تبدأ من بند
العميل. وإذا فُتح طلب مورد واحد لكل مورد (والمعتاد أن يوزَّع بند العميل على عدة
موردين)، يُنشأ **إسناد مكرر/متعارض لنفس بند العميل**.

**التوصية:** `customer_rfq_items` هو **مصدر الحقيقة الوحيد** للمسؤولية. تُنقل
`rfq_item_assignments` لتصبح إسنادات على مستوى بند العميل، و`rfq_items` **يقرأ**
المسؤولية عبر الرابط الموجود `rfq_items.customer_rfq_item_id` دون إنشاء مسؤولية
مستقلة.

## 2. العلاقات الفعلية في قاعدة البيانات (مُتحقَّق منها من الـschema)

### 2.1 خريطة العلاقات

```
customers
   │
customer_rfqs ──────────────┐ (id)
   │                        │
customer_rfq_items ─────────┤ id  ← المصدر المطلوب للمسؤولية
   │  (id)                  │
   │                        │
   │  rfq_items.customer_rfq_item_id  (FK, ON DELETE SET NULL)
   │                        │
   │                   rfq (id)
   │                        │
   │                   rfq_items (id)
   │                        │
   │                   offers (id) ── offer_items.rfq_item_id ──┐
   │                        │                                    │
   │                   purchase_orders.rfq_id (header-level)    │
   │                        │                                    │
   │                   purchase_order_items.po_id               │
   │                        │                                    │
   └──── customer_po_items.customer_rfq_item_id ─── customer_pos  │
                                                                │
   customer_po_items ── purchase_order_items.customer_po_item_id ┘
```

### 2.2 الروابط المؤكدة (موجودة اليوم)

| من                                          | إلى                     | النوع             | ملاحظة                                         |
| ------------------------------------------- | ----------------------- | ----------------- | ---------------------------------------------- |
| `rfq_items.customer_rfq_item_id`            | `customer_rfq_items.id` | FK (SET NULL)     | **الرابط الحاسم** — يصل بند المورد بأصل العميل |
| `offers.rfq_id` → `offer_items.rfq_item_id` | `rfq_items.id`          | FK                | العروض على مستوى بند المورد                    |
| `purchase_orders.rfq_id`                    | `rfq.id`                | FK (header-level) | **لا يوجد** رابط بند↔بند مع PO                 |
| `purchase_order_items.customer_po_item_id`  | `customer_po_items.id`  | FK                | يربط بند أمر الشراء ببند أمر العميل            |
| `customer_po_items.customer_rfq_item_id`    | `customer_rfq_items.id` | FK (SET NULL)     | يربط أمر العميل بأصل بند طلب العميل            |
| `customer_po_items.customer_po_id`          | `customer_pos.id`       | FK (nullable)     | الإلغاء الناعم يجعلها NULL                     |

### 2.3 نقاط مؤكدة بالفحص (لا افتراض)

1. **لا يوجد FK مباشر `rfq_item → po_item`.** الإصلاح في المرحلة 2 (تم) يعتمد
   مطابقة هوية داخل أوامر الشراء **المرتبطة بالـRFQ نفسه**.
2. **`rfq_items.customer_rfq_item_id` يُملأ من الواجهة فقط.** `POST /rfq` يقبله من
   `items[].customerRfqItemId`، والواجهة ترسله عندما يُفتح طلب المورد **من داخل
   بند العميل**. طلب المورد المُنشأ يدويًا لا يحمل الرابط (NULL).
3. **`customer_rfq_items.category_id` موجود في الـDDL بلا FK وبلا استخدام.**
4. **الإسناد الحالي يُنشأ على مسارين:** `POST /rfq` (تلقائي) و
   `PATCH /rfq/items/:itemId/assignment` (يدوي) — كلاهما على `rfq_items`.

## 3. المشكلة الجوهرية في التصميم الحالي

**سيناريو واقعي:** طلب عميل فيه 5 بنود (قاطع، كابل، مروحة، فلتر، مقاوم حريق).
المشتريات توزّعه على 3 موردين ⇒ 3 طلبات مورد، كل واحد يحمل نفس بنود العميل عبر
`customer_rfq_item_id`.

| البند                       | ما يحدث اليوم                               |
| --------------------------- | ------------------------------------------- |
| بند العميل «مروحة»          | **لا مسؤول له** (لا يُصنَّف ولا يُسنَد)     |
| بند المورد (مورد أ) للمروحة | يُصنَّف ويُسنَد لموظف — `source: auto`      |
| بند المورد (مورد ب) للمروحة | يُصنَّف ويُسنَد لموظف **آخر** (توزيع الحمل) |

**النتيجة:** مسؤولان مختلفان لنفس بند العميل بلا سبب واضح — وهو ما طلبتَ منعه
صراحةً. وأسوأ: KPI يقيس **عدد بنود طلبات الموردين**، فيتضخّم الرقم بتكرار البند
لكل مورد، ويصبح المؤشر «كم طلب تسعير تعامل معه الموظف» بدل «كم بند عميل أنجزه».

## 4. خيارات التصميم

### الخيار A — إبقاء الإسناد على `rfq_items` مع دمج عبر الرابط (مرفوض)

تُقرأ المسؤولية من بنود الموردين ثم تُنسب لبند العميل عبر `customer_rfq_item_id`.

- ❌ لا يحلّ عدم وجود مسؤول **قبل** إصدار طلب المورد.
- ❌ يبقي التكرار قائمًا (3 إسنادات لنفس بند العميل).
- ❌ KPI يظل على مستوى بند المورد.

### الخيار B — نقل الإسناد إلى `customer_rfq_items` (الموصى به)

`rfq_item_assignments` تصبح إسنادات على بند العميل، و`rfq_items` **يقرأ** المسؤولية.

- ✅ المسؤولية تُنشأ عند استلام طلب العميل (بداية الدورة الفعلية).
- ✅ إسناد واحد لكل بند عميل مهما تعدد الموردون.
- ✅ KPI على مستوى بنود العملاء (الصحيح).
- ✅ يستهلك الجداول الموجودة (لا إعادة كتابة)، والرابط `customer_rfq_item_id` قائم.

### الخيار C — إبقاء الجدولين مع مصدر حقيقة واحد (بديل انتقالي)

جدول إسناد على بند العميل (مصدر الحقيقة) + جدول على بند المورد **للقراءة فقط**
(مشتق، لا يُنشئ مسؤولية). تعقيد أكبر بلا فائدة إذا اعتمدنا B، لكنه مفيد كجسر إذا
تعذّر نقل الجدول فورًا. **غير موصى به** لأنه يُبقي احتمال التعارض قائمًا.

**القرار المقترح: B.**

## 5. التصميم المقترح تفصيلًا (الخيار B)

### 5.1 مصدر الحقيقة

| السؤال                      | الجواب في التصميم الجديد                           |
| --------------------------- | -------------------------------------------------- |
| أين تُصنَّف البنود؟         | `customer_rfq_items.category_id`                   |
| أين تُسجَّل المسؤولية؟      | جدول الإسناد، عموده الرئيسي `customer_rfq_item_id` |
| ما الذي يقيسه KPI؟          | بنود طلبات العملاء (`customer_rfq_items`)          |
| كيف تُقرأ المسؤولية لاحقًا؟ | عبر الرابط `rfq_items.customer_rfq_item_id`        |

### 5.2 شكل جدول الإسناد

الأنسب: **إعادة استخدام `rfq_item_assignments`** مع نقل المفتاح الأساسي المنطقي إلى
بند العميل. لكن الاسم سيصبح مضلِّلًا. خياران:

- **(B1) إعادة تسمية** إلى `customer_rfq_item_assignments` مع عمود
  `customer_rfq_item_id UNIQUE` (استبدال `rfq_item_id`). أنظف دلاليًا.
- **(B2) إبقاء الاسم** `rfq_item_assignments` وإضافة `customer_rfq_item_id`
  كعمود فريد، مع إبقاء `rfq_item_id` nullable/مشتقًا. أقل تغييرًا لكن الاسم يكذب.

**الموصى به: B1** (إعادة تسمية + ترحيل)، لأن اسم الجدول يجب أن يصف ما يفعله فعلًا —
وهذا نفس مبدأ إصلاح سجل «engine: mastra» الكاذب في هذا المستودع.

### 5.3 الحقول المقترحة للجدول

```
customer_rfq_item_assignments
  id                 SERIAL PK
  customer_rfq_item_id  INTEGER NOT NULL UNIQUE → customer_rfq_items(id) ON DELETE CASCADE
  category_id        INTEGER → item_categories(id) ON DELETE SET NULL
  employee_id        INTEGER → employees(id) ON DELETE SET NULL
  source             TEXT NOT NULL DEFAULT 'auto'   -- auto | manual | inherited
  confidence         NUMERIC(5,2)
  assigned_by        INTEGER → employees(id) ON DELETE SET NULL
  assigned_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

- `UNIQUE(customer_rfq_item_id)` = إسناد واحد لكل بند عميل — **يمنع التعارض بنيويًا**.
- `source` يضيف `inherited` لتمييز إسناد موروث (للتتبع فقط).

## 6. كيف تنتقل/تُقرأ المسؤولية في المراحل التالية

| المرحلة                                 | كيف تُقرأ المسؤولية                                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **بند طلب المورد** (`rfq_items`)        | عبر `rfq_items.customer_rfq_item_id` → إسناد بند العميل. إن كان NULL (طلب مورد يدوي بلا أصل) ⇒ **لا مسؤول** ويُعرض كذلك صراحةً. |
| **عرض المورد** (`offers`/`offer_items`) | عرض المورد مرتبط ببند مورد مرتبط ببند عميل ⇒ «من حصل على العرض» = مسؤول بند العميل.                                             |
| **أمر الشراء** (`purchase_order_items`) | عبر `customer_po_item_id` → `customer_rfq_item_id` → المسؤول.                                                                   |
| **أمر العميل** (`customer_po_items`)    | عبر `customer_rfq_item_id` مباشرةً.                                                                                             |

**قاعدة عدم التعارض (مُطبَّقة في الكود):** إذا كان لبند المورد `customer_rfq_item_id`
فإن مسؤوليته **تُقرأ فقط** ولا تُنشأ أبدًا. تُنشأ مسؤولية مستقلة **فقط** لبند مورد
بلا أصل (NULL) — ويُوسم `source: auto` بوضوح مع تعليق يشرح السبب.

> **ملاحظة مهمة:** هذه القاعدة نفسها تنطبق على **التصنيف**: بند المورد الموروث
> **لا يُصنَّف مجددًا**، بل يقرأ تصنيف بند العميل. هذا يمنع أن يختلف تصنيف البند عن
> تصنيف أصله (نفس عائلة العيب الذي منعك منه).

## 8. خطة ترحيل البيانات (دون فقدان أو تكرار)

الترحيل يجب أن يكون **idempotent** ويعمل ضمن `init-db.ts` (كل عبارة في
`client.query` مستقلة — قاعدة المستودع).

### الخطوات

1. **إنشاء الجدول الجديد** `customer_rfq_item_assignments` (CREATE TABLE IF NOT EXISTS
   - UNIQUE + فهارس) — عبارة مستقلة.
2. **نقل الإسنادات ذات الأصل:** من `rfq_item_assignments` حيث
   `rfq_items.customer_rfq_item_id IS NOT NULL` ⇒ إدراج في الجدول الجديد بمفتاح
   `customer_rfq_item_id`.
   - عند تعدد إسنادات الموردين لنفس بند العميل: نأخذ **واحدًا فقط** بترتيب حتمي
     (`min(id)` أو الأحدث `assigned_at` ثم `id`) ونوسمه `source='inherited'`.
     هذا يمنع تكرار الصف في الجدول الجديد (UNIQUE).
3. **الإسنادات بلا أصل** (`customer_rfq_item_id IS NULL`): لا تُنقل إلى بند عميل
   (لا أصل لها). خياران:
   - (أ) تُترك في الجدول القديم حتى إعادة التصنيف، أو
   - (ب) تُنقل إلى إسناد «مستقل» على مستوى بند المورد في جدول منفصل.
     **الموصى به (أ)** مع تقرير عددي للمشرف: «N إسناد بلا أصل — يحتاج إعادة تصنيف».
4. **عدم حذف الجدول القديم فورًا.** يبقى للقراءة حتى انتهاء التحقق، ثم حذفه في
   مرحلة لاحقة منفصلة.
5. **التحقق بعد الترحيل:** استعلام يقارن عدد بنود العملاء التي لها إسناد قبل/بعد،
   ويطبع تقريرًا (لا يفشل الإقلاع).

### المخاطر المُرصودة

| الخطر                                              | التخفيف                                                                 |
| -------------------------------------------------- | ----------------------------------------------------------------------- |
| إسنادان لبند عميل واحد                             | UNIQUE + اختيار حتمي `min(id)`                                          |
| فقد إسنادات يدوية                                  | تُنقل بوسم `manual` (أولوية أعلى من `auto`)                             |
| إسنادات بلا أصل                                    | تُترك + تقرير، لا حذف صامت                                              |
| FK `ON DELETE SET NULL` على `customer_rfq_item_id` | البند يُحذف نادرًا؛ مع CASCADE على الجدول الجديد نمنع الإسنادات اليتيمة |

## 10. جدول `item_category_keywords` (القرار الثاني)

### 10.1 الشكل

```
item_category_keywords
  id           SERIAL PK
  category_id  INTEGER NOT NULL → item_categories(id) ON DELETE CASCADE
  keyword      TEXT NOT NULL              -- الكلمة أو العبارة (خام)
  weight       INTEGER NOT NULL DEFAULT 0 -- 0 ⇒ استخدم الوزن الافتراضي حسب النوع
  language     TEXT                        -- 'ar' | 'en' | NULL (للفلترة والعرض)
  enabled      BOOLEAN NOT NULL DEFAULT true
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
  UNIQUE (category_id, keyword)            -- منع التكرار داخل التصنيف
```

### 10.2 القواعد المطلوبة وكيف تُنفَّذ

| المطلوب                                 | التنفيذ                                                            |
| --------------------------------------- | ------------------------------------------------------------------ |
| كلمات عربية وإنجليزية                   | عمود `language` + نفس منطق `normalizeText` الحالي                  |
| عبارات كاملة وكلمات منفردة              | العبارة تُكتشف بوجود مسافة (نفس `isPhrase` الحالي)                 |
| وزن لكل كلمة                            | `weight`؛ `0` يعني الوزن الافتراضي (`W_PHRASE`/`W_TOKEN`)          |
| تعديل/حذف                               | CRUD كامل بصلاحية `item-categories:manage`                         |
| منع التكرار                             | `UNIQUE(category_id, keyword)` + تطبيع قبل الإدراج                 |
| تعطيل دون حذف                           | `enabled=false` يُستثنى من التحميل                                 |
| **تصنيف جديد لا يعمل قبل إعداد كلماته** | المصنّف يقرأ من الجدول؛ تصنيف بلا كلمات مُفعَّلة ⇒ لا يُنتج مرشحًا |
| الاحتفاظ بالعتبة ومنع التخمين           | يبقى `MIN_CONFIDENCE` + قاعدة التعادل كما هي                       |

### 10.3 عدم خفض دقة المصنّف (شرط صريح)

**الخطر:** نقل الكلمات من الكود إلى الجدول قد يفقد كلمة أو يغيّر وزنها ⇒ انخفاض دقة.
**التخفيف:**

1. **البذر (seed) يُنشأ من نفس ثوابت الكود الحالية** `CATEGORY_KEYWORDS` — تُدرج
   كصفوف أولية عند الإقلاع (idempotent). لا كلمة تُفقد.
2. **المصنّف يقرأ من الجدول، ويسقط إلى ثوابت الكود إذا كان الجدول فارغًا** —
   فلا يتوقف التصنيف أبدًا حتى لو فشل البذر.
3. **حارس اختبار:** يقارن الكلمات المُبذورة (بعد التطبيع) مع `CATEGORY_KEYWORDS`،
   ويفشل إذا نقصت كلمة. هذا يمنع الانحدار الصامت في الدقة.
4. الأوزان المخصّصة (`weight`) تُضاف للأوزان الافتراضية، لا تستبدلها، حتى لا يقل
   وزن دليل قائم.

### 10.4 مسار القراءة في المصنّف

```
loadClassifierKeywords()          // الجدول → Map<code, [{term, weight, isPhrase}]>
   │  (fallback: CATEGORY_KEYWORDS إن كان الجدول فارغًا)
classifyItem(input, categories, keywords)   // نفس الخوارزمية، مصدر كلمات مُمرَّر
```

تُمرَّر الكلمات **كوسيط** (لا تُقرأ داخل الدالة) حتى تبقى `classifyItem` نقية
وقابلة للاختبار بلا قاعدة بيانات — نفس مبدأ اليوم.

## 13. المخاطر والقرارات المطلوبة

### مخاطر

1. **الترحيل** — إسنادات متعددة لنفس بند العميل؛ التخفيف: UNIQUE + اختيار حتمي.
2. **إسنادات بلا أصل** — لا تُنقل؛ تبقى + تقرير.
3. **دقة المصنّف** — التخفيف: بذر من الكود + حارس اختبار + fallback.
4. **توسّع النطاق** — بنود العملاء أكثر بكثير من بنود الموردين؛ التصنيف التلقائي
   عند الإنشاء قد يكون ثقيلًا ⇒ يُنفَّذ best-effort (لا يفشل إنشاء الطلب).

### قرارات مطلوبة منك

1. **اسم الجدول:** إعادة تسمية (`customer_rfq_item_assignments`) أم إبقاء الاسم
   القديم (B2)؟
2. **الإسنادات بلا أصل:** تُترك للتصنيف اليدوي (أ) أم تُنقل لمكان مستقل (ب)؟
3. **توقيت الإسناد:** عند **إنشاء** طلب العميل فقط، أم أيضًا عند **تعديل** بنوده؟
4. **حذف الجدول القديم:** في نفس المرحلة أم مرحلة لاحقة بعد التحقق؟

## 14. الخلاصة

- **مصدر الحقيقة للمسؤولية:** `customer_rfq_items` (عبر جدول إسناد على بند العميل).
- **`rfq_items`:** يقرأ المسؤولية الموروثة، ولا يُنشئ مسؤولية مستقلة عند وجود أصل.
- **KPI:** على بنود العملاء، مع فصل واضح لغير المُصنَّف/غير المُسنَد.
- **الكلمات المفتاحية:** جدول `item_category_keywords` قابل للإدارة، مع بذر من
  الكود وحارس يمنع انخفاض الدقة.

> **لا تنفيذ قبل اعتماد هذا التصميم.** المراحل 1–3 منتهية ومختبرة؛ المراحل 4–8
> تنتظر قرارك في البنود الأربعة أعلاه.
